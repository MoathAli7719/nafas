الفصل 1: لماذا المشروع مهم؟

نظرة عامة على المشروع

ملخص سريع يوضح ماذا بنينا، لماذا بنيناه، وما القيمة التقنية التي تميز المشروع.

المشكلة

صعوبة وصول الأسر المنتجة/الطهاة المنزليين إلى العملاء بشكل منظم، وغياب منصة توفر إدارة منتجات + طلبات + متابعة حالة + إشعارات + رقابة.

الحل

منصة (Customer / Chef / Admin) في تطبيق واحد مبني بـ Flutter، مع Backend سحابي (Firebase) ورفع صور عبر Cloudinary، وتحديث لحظي عبر Streams.

القيمة الهندسية (Software Engineering)

تنظيم كود بمعايير Clean Architecture + تطبيق SRP/DRY + عزل صلاحيات + تدفقات Real-time + جاهزية للنشر (Signing/Keystore).

الفصل 4: المتطلبات والجودة

متطلبات المشروع

متطلبات وظيفية وغير وظيفية لتوضيح حجم الإنجاز وجودة التطبيق.

متطلبات وظيفية (Functional)

  • تسجيل/تسجيل دخول + إدارة جلسة المستخدم.
  • نظام أدوار وصلاحيات (Admin/Chef/Customer).
  • CRUD للمنتجات + التحكم في توفر المنتج.
  • إنشاء الطلبات + تحديث حالة الطلب + أرشفة.
  • طلبات اشتراك: قبول/رفض + سبب + إشعارات.
  • رفع صور متعددة + قص/جودة + حد أقصى.

متطلبات غير وظيفية (Non‑Functional)

  • Security: عزل البيانات وقواعد Firestore.
  • Maintainability: SRP/DRY + Layers.
  • Reliability: try/catch + رسائل أخطاء واضحة.
  • Performance: ضغط الصور + رفع متوازي.
  • Scalability: تصميم Collections قابل للتوسع.

المدة الزمنية للمشروع

تم إنجاز المشروع وفق منهجية هندسية شملت: تحليل المتطلبات، بناء الهيكلية، تطوير الميزات (Customer/Chef/Admin)، ثم الاختبار والتحسين النهائي.

الفصل 5: الهيكلة والتنظيم

الهيكلة (Architecture) وجودة الشفرة البرمجية

كيف ضمنّا جودة الشفرة البرمجية؟ كيف فصلنا UI/Logic/Data؟ وكيف انعكس ذلك على تسريع تطوير الـ Features؟

Single Responsibility

تم تقسيم الكود وفق مبدأ Single Responsibility (SRP) لضمان أن كل كلاس مسؤول عن وظيفة واحدة فقط، مما يسهل الصيانة والاختبار.

Clean Structure

هيكل المجلدات يتبع معايير Clean Architecture: طبقة الـ Data (Models/Repo Impl)، وطبقة الـ Domain (Contracts/Entities)، وطبقة الـ Presentation (UI/Providers).

DRY Principle

تطبيق مبدأ DRY عبر Core Widgets موحدة + ثوابت تصميم (Colors/Styles) لتقليل التكرار وتسهيل التحديث الشامل.

// هيكل المجلدات (Clean Architecture)
lib/
├── core/ // Shared logic, themes, constants
├── features/
│ └── product/
│ ├── data/ // Data Sources & Repo Implementations
│ ├── domain/ // Entities & Abstract Repositories
│ └── presentation/ // ViewModels (Providers) & UI Pages
الفصل 6: نموذج البيانات

نموذج البيانات (Firestore)

تفصيل الـ Collections الرئيسية وما الهدف منها وكيف يتم ربطها بالأدوار والصلاحيات.

users

معلومات المستخدم + الدور + بيانات المطبخ + حالة الاشتراك + حالة طلب الشيف.

  • role / uid / displayName / phoneNumber
  • chefRequestStatus / chefRequestMessage
  • restaurantName / category / isAvailable / coverImageUrl
  • isSubscribed / subscriptionType / subscriptionExpiry

products

كل منتج مرتبط بـ chefId ويحتوي صور متعددة (imageUrls) وسعر وتوفر وتصنيف.

  • chefId + chefName
  • imageUrls (حتى 6)
  • price + isAvailable + createdAt

orders

طلبات مرتبطة بالشيف ويتم تحديثها لحظياً عبر Streams، مع status + timestamps.

  • status: pending / accepted / completed
  • updatedAt + acceptedAt + completedAt
  • totalPrice + items + customerId

subscription_requests

طلبات الاشتراك التي يراجعها الأدمن: status + planType + expiryDate + rejectReason.

  • approve/reject عبر Firestore batch
  • حفظ سبب الرفض وإشعار المستخدم
// ملاحظة هندسية
استخدمنا تحديثات Batch في الأدمن لمنع "نصف تحديث" بين وثيقة الطلب ووثيقة المستخدم.
الفصل 7: رحلة تنفيذ المميزات

رحلة تنفيذ المميزات (Features)

1. Core System & Role-Based Auth

Firebase Auth + AuthProvider يستمع لحالة تسجيل الدخول ويجلب UserModel من Firestore، ويعمل Listener على وثيقة المستخدم لتحديث الواجهات لحظياً.

2. Kitchen Management (Chef)

تعديل بيانات المطبخ + حالة Open/Closed + رفع صورة الغلاف عبر Cloudinary ثم تحديث Firestore في نفس الشاشة.

3. Dynamic Marketplace (Customer)

تصفح ذكي للمنتجات، نظام تصنيفات، وعربة تسوق تدعم الطلب من عدة طباخين في وقت واحد.

4. نظام الطلبات المتقدم (الميزة الختامية)

ميزة الطلبات هي قلب المشروع: إنشاء الطلب وتخزينه، ثم متابعة الحالة لحظياً عبر Streams لكل دور، مع timestamps وإشعارات عند التحديث.

الفصل 8: نظام الطلبات

تفاصيل نظام الطلبات (Deep Dive)

شرح معماري تفصيلي لنظام الطلبات: حالات، تزامن، تحديثات، وإدارة الأخطاء.

دورة حياة الطلب

الحالة تُخزن كنص (status.name) وتُحدّث مع updatedAt، وعند قبول الطلب أو إكماله يتم حفظ acceptedAt/completedAt.

lifecycle
pending → accepted → completed

التحديث اللحظي (Streams)

الشيف يشاهد الطلبات عبر getChefOrdersStream(chefId) بحيث يتم تحديث القائمة مباشرة عند أي تغيير في Firestore.

الاعتمادية

try/catch ورسائل واضحة، وترتيب الطلبات حسب createdAt لضمان رؤية الأحدث أولاً.

الفصل 9: الأدمن والتحكم

لوحة الأدمن (الاشتراكات)

قبول/رفض طلبات الاشتراك يتم بشكل آمن وذري عبر Firestore Batch لضمان عدم حدوث نصف تحديث.

تحديث ذري (Batch)

عند القبول: تحديث subscription_requests + users في نفس العملية ثم commit.

  • status = approved
  • startDate / expiryDate
  • storeStatus = active

قبول + إشعار

بعد commit يتم إرسال إشعار للشيف بنجاح التفعيل عبر NotificationService.sendAdminNotification.

رفض + سبب

رفض الطلب مع سبب يتم حفظه في الطلب والمستخدم، ثم إرسال إشعار يوضح السبب.

الفصل 10: الإشعارات

الإشعارات (FCM)

الإشعارات تربط الأدوار الثلاثة وتُستخدم في: طلبات الانضمام، الاشتراكات، وتحديثات الطلبات.

تحديث Token

عند تسجيل الدخول يقوم AuthProvider باستدعاء NotificationService.updateToken لضمان وصول إشعارات الحساب الصحيح.

إشعارات موجهة

الأدمن يرسل إشعار موجه للشيف عند قبول/رفض الاشتراك، مع حفظ سجل في admin_notifications.

عزل المسؤوليات

المنطق موجود داخل Service وليس في UI، مما يحقق SRP ويسهل إعادة الاستخدام.

الفصل 11: الأمان والنشر

Security & Deployment

تفصيل النشر والأمان: Keystore/Signing/Signature + خطة CI/CD (غير مطبقة حالياً) + iOS دون Mac.

Keystore & Signing

إعداد مفاتيح التوقيع (Keystore) لتأمين التطبيق وضمان سلامة الشفرة البرمجية عند رفعه للمتاجر.

  • إنشاء keystore وإبقاؤها خارج Git
  • ربطها بملف gradle لنسخة Release
  • إدارة كلمات المرور عبر بيئة آمنة (ENV)

خطوات النشر (Deployment)

فهم آلية الـ Deployment للأندرويد و iOS، والتعامل مع متطلبات الـ App Store و Play Store.

  • إنتاج AAB للأندرويد و IPA للـ iOS
  • تجربة إصدار تجريبي عبر TestFlight
  • مراجعة الإصدارات وتوثيق التغييرات

App Signature

استخدام Application Signature لتوثيق هوية التطبيق ومنع التلاعب بنسخة الـ APK/IPA.

  • حماية ملكية التطبيق على المتجر
  • منع أي جهة من رفع تحديث باسم التطبيق دون توقيع صحيح

CI/CD (خطة — غير مطبقة حالياً)

حسب توجيه الدكتور، هذه هي الخطة التي سنطبقها/نجهزها خلال أسبوع التسليم:

  • تحليل الكود + فحص التنسيق
  • Build Android Release
  • تجهيز iOS build عبر خدمة سحابية عند عدم توفر Mac

بناء iOS دون Mac

استخدام Codemagic/Appcircle لبناء iOS وإدارة Certificates وProvisioning Profiles ثم الرفع إلى TestFlight.

ملاحظات أمنية

اعتماد قواعد Firestore + عزل البيانات حسب الدور/uid + عدم تضمين Secrets ضمن الشفرة البرمجية.

الفصل 13: تحديات تقنية وحلول هندسية

تحديات واقعية (تُظهر المجهود المبذول)

أمثلة عملية توضّح كيف واجهنا تعقيدات البرمجة وحللناها عبر حلول منظمة ومستقرة.

1. تحدي: تزامن بيانات المستخدم

المشكلة: عند تغيير دور المستخدم أو قبول اشتراكه، كانت الواجهات تتطلب إعادة تشغيل التطبيق لتحديث الصلاحيات.

الحل: تفعيل الـ Listener داخل AuthProvider لمراقبة وثيقة المستخدم في Firestore لحظياً، مما يجعل التطبيق يستجيب لأي تغيير في الصلاحيات دون تدخل المستخدم.

AuthProvider: _startUserDocListener

2. تحدي: سلامة البيانات (Data Integrity)

المشكلة: عند قبول اشتراك الشيف، نحتاج لتحديث حالته في "طلبات الاشتراك" وفي "بيانات المستخدم" في نفس الوقت، وحدوث خطأ في أحدهما قد يسبب تعارضاً.

الحل: استخدام WriteBatch لضمان تنفيذ العمليتين معاً بشكل "ذري" (Atomic)؛ إما أن ينجح التحديث للطرفين أو يفشل للكل، لضمان استقرار قاعدة البيانات.

AdminSubscriptionRequestsPage: batch.commit()

3. تحدي: أداء رفع الوسائط المتعددة

المشكلة: رفع 6 صور عالية الجودة واحدة تلو الأخرى يسبب بطءاً شديداً وتجربة مستخدم سيئة.

الحل: استخدام Future.wait لتنفيذ عمليات الرفع إلى Cloudinary بشكل متوازٍ (Parallel)، مما قلل وقت الانتظار بنسبة تزيد عن 60% مع إضافة ضغط وقص للصور قبل الرفع.

AddProductPage: Future.wait(uploadTasks)
الفصل 14: نقاط التقييم

نقاط تقييم الدكتور (Checklist)

Architecture + تنظيم المشروع

  • Clean Architecture (Data/Domain/Presentation)
  • SRP: Providers/Repositories/Services

قاعدة البيانات وربطها بالميزات

  • Firestore collections واضحة

توزيع مهام الفريق

هذا هو تقسيم العمل الحقيقي داخل فريق نَفَس كما تم تنفيذه أثناء تطوير الشفرة البرمجية، مع توزيع واضح لأجزاء العرض والديمو.

معاذ

Leader + Backend + Deployment

مسؤول عن قيادة الفريق، وربط أجزاء النظام، والمهام الخلفية (Firebase/Repositories) وتجهيز النشر.

  • في العرض: نظرة عامة + نطاق المشروع + المتطلبات + النشر/Signing + خطة CI/CD
  • في الديمو: تأكيد تشغيل المشروع على Emulator وحسابات جاهزة
  • نقطة تقنية: تدفقات البيانات + Repositories + Order logic (حسب التنفيذ)
مريم

واجهات الشيف (Chef UI)

مسؤولة عن بناء وتجهيز شاشات الشيف وتجربة استخدامها (إضافة منتج، تعديل بيانات المطبخ، استقبال الطلبات).

  • في العرض: مميزات الشيف + مبررات UX + إدارة الصور
  • في الديمو: إضافة منتج بصور متعددة + تعديل بيانات المطبخ
  • نقطة تقنية: Cloudinary upload + ImagePicker/Cropper + Validation
هيله

واجهات العميل (Customer UI)

مسؤولة عن رحلة العميل داخل التطبيق: تصفح، اختيار منتجات، وإكمال الطلب ومتابعة الحالة.

  • في العرض: رحلة العميل + قرارات سهولة الاستخدام
  • في الديمو: إنشاء Order ومتابعة تغيّر الحالة
  • نقطة تقنية: التعامل مع الحالة (Providers) وتحديثات real-time في الواجهة
آيات

واجهات الأدمن (Admin UI)

مسؤولة عن شاشات الإدارة: مراجعة طلبات الاشتراك، القبول/الرفض مع سبب، وإظهار الأثر على حساب الشيف.

  • في العرض: صلاحيات الأدمن + لماذا استخدمنا Batch updates
  • في الديمو: فتح subscription requests ثم Approve/Reject وإظهار الإشعار
  • نقطة تقنية: Firestore Batch + إرسال إشعار موجه

أسئلة متوقعة (جاهزة للتقييم)

لماذا Clean Architecture؟

لأنه مشروع متعدد الأدوار والميزات. الفصل بين الطبقات يقلل التعقيد ويسهل إضافة Features جديدة بدون كسر النظام.

كيف أثبتّم الالتزام بـ SRP/DRY؟

Providers لإدارة الحالة فقط، Repositories للبيانات فقط، Services للإشعارات/الرفع فقط، مع Widgets مشتركة وثوابت تصميم مركزية.

كيف ضمنتم الأمان؟

Firebase Auth + عزل البيانات حسب uid + قواعد Firestore + عدم رفع أسرار + Signing للتطبيق عند النشر.

كيف النظام لحظي؟

Firestore snapshots/Streams للطلبات وتحديثات المستخدم والإحصائيات، مما يلغي الحاجة للـ Refresh.
